# DXSharp 0.4.0-preview.4

This preview adds a modern Framework/character-animation foundation, precompiled shader tooling, native Win32/WPF/WinUI hosting, readback and texture-transfer APIs, and reusable Media Foundation playback. The SDK remains a Windows x64 preview with explicit ownership and synchronization contracts.

## Packages and runtime targets

The qualified set now contains ten package IDs: `DXSharp.Native`, `DXSharp.Core`, `DXSharp.Assets`, `DXSharp.DirectML`, `DXSharp.Framework`, `DXSharp.Framework.Desktop`, `DXSharp.Framework.Wpf`, `DXSharp.Framework.WinUI`, `DXSharp.Media`, and `DXSharp.Tools.Builds`. Each has a matching symbol package; release assets include a SHA-256 manifest bound to the exact release commit.

Modern Windows libraries target .NET 10 and .NET 11 with Windows SDK target 10.0.26100.0. Assets targets portable net10.0/net11.0; the MSBuild task targets netstandard2.0. Samples default to .NET 10; select .NET 11 with `-p:DXSharpRuntimeMajor=11`. Building the repository uses SDK 11.0.100. The graphics/runtime qualification remains Windows x64; Linux evidence covers portable COM/CPU fixtures, not a DirectX renderer.

Dependency pins remain Agility 1.620.2, DXC 1.9.2609.5, DirectML 1.15.4, CsWin32 0.3.371 and Win32Metadata 71.0.45-preview. The optional WinUI adapter pins Microsoft.WindowsAppSDK.WinUI 2.7.0. WPF, WinUI, DirectML and media packages are selected independently; Core does not acquire a desktop UI framework or a proprietary Noesis dependency.

## Framework and character rendering

Framework now supplies instance-owned game timing, animation playback and persistent GPU skinning/material rendering. CharacterLab exercises real clips, interpolation/fades, horizontal root-motion handling, four material maps and fence-retired frame slots. Asset validation rejects unsupported data explicitly. The WinForms, native Win32, WPF and WinUI variants share the scene and renderer rather than maintaining separate character implementations.

**Breaking migration:** the old experimental RCW-dependent `DXSharp.Framework` surface has been replaced. Removed APIs include AppManager, ThreadSystemBase, miscellaneous lifecycle/debug/display helpers, Compressor/FolderEnumeration, IScreen and related extension/data types. Existing consumers must retain their previous version or migrate; this is not a transparent binary replacement. Original DXSharp and DXSharp.Dxc compatibility projects remain separate. See [Framework vision and migration](https://github.com/atcarter714/DXSharp/blob/main/doc/Framework-Vision.md).

## Shader build and window hosts

`DXSharp.Tools.Builds` compiles `DXSharpShader` items with DXC during MSBuild, including multiple stages/permutations, actual transitive includes, collision checks and dependency/hash manifests. Shaders can be embedded or staged as content. The compiler path can be overridden for cross-compilation. Core adds typed compilation options and owned bytecode loading; applications that only load precompiled shaders can disable DXC DLL staging. Build-time DXIL does not precompile a portable driver PSO.

The shared FrameRenderer owns presentation resources and retired frame slots. NativeGame provides a lightweight Win32 window/message loop without WinForms. Desktop retains its WinForms API. Optional WPF uses a child HWND; optional WinUI uses a composed SwapChainPanel with XAML overlays. Physical-pixel sizing, focus, DPI/scale and orderly stop/drain ownership are documented per host.

WinUI now queues drawing after the XAML composition callback, polls GPU fences, retries busy presentation, drains resize work on a worker and reattaches resized swap chains. Skipped GPU-busy turns retain elapsed animation time. Samples persist lifecycle/HRESULT diagnostics and bounded qualification watchdogs. The reported Roci VideoPlayer crash and move/resize freeze were resolved in the accepted hardware review.

## Readback and texture transfers

Bounded readback rings join descriptor pools and upload rings. Typed single-plane sampled Texture2D descriptions support explicit mips, arrays and cube arrays; transfers use native footprints to handle row/placement padding and BC blocks. GPU-gated fixtures verify exact bytes, partial updates, early owner disposal and safe retirement. The caller still owns barriers and queue ordering.

DDS parsing, automatic mip generation, depth/video planes, general render/UAV texture descriptions and GPU-side cross-queue handoffs remain separate work. See [texture-transfer contracts](https://github.com/atcarter714/DXSharp/blob/main/doc/tutorials/09-texture-transfers.md).

## Media playback and native coverage

The optional MediaPlayer uses Media Foundation Media Engine for local-file playback, audio output and the A/V presentation clock. The WinUI VideoPlayer demonstrates play/pause, seeking, looping, file selection, volume/mute and reusable video-texture rendering. Frames carry native PTS and source/seek generations; per-slot textures avoid alternating stale frames.

The actual backend is **Media Foundation → writable WIC BGRA → CPU staging → D3D12 upload**. It is an SDR 8-bit baseline, with decoder acceleration unmeasured. No zero-copy, HDR, network/protected-media, direct D3D12 video-queue or measured physical speaker-latency claim is made.

Native projects the complete pinned Media Foundation namespace, including its D3D12 video declarations. The name/member/IID gate measures 1,650 top-level types and 8,484 member names. Declaration coverage is not comprehensive ABI, codec or hardware qualification. See [media contracts](https://github.com/atcarter714/DXSharp/blob/main/doc/Media-Playback.md).

## Qualification and known issues

The code baseline passed [all six qualification jobs](https://github.com/atcarter714/DXSharp/actions/runs/45662746089): Windows Debug/Release, .NET 10/11 native COM JIT/NativeAOT on Windows/Linux, Windows source-sample runs, and all 17 isolated package consumers on both runtimes/configurations. Portable fixtures report 2,298 checks with no live native objects. WARP runs check WinUI resize/scale/focus/lifecycle/failure/restart, video colors/clock/pause/seek/loop/reopen/drained shutdown, and the existing rendering/compute workloads. The release workflow requalifies the exact release commit before publication, then verifies clean NuGet.org-only consumers and the public DXC MSBuild task on both runtimes after upload.

Aaron accepted functionality/stability on Roci's RTX 3080 Ti on 2026-11-25, reporting smooth/snappy WinUI samples and resolved crashes. This is workstation acceptance, not a cross-vendor soak, acceleration measurement or physical audio-latency benchmark. Optional desktop/media workloads are JIT-qualified; separate SDK NativeAOT gates do not establish WPF/WinUI/media NativeAOT support.

Known UI polish: WinUI volume and animation-speed sliders currently step too coarsely in whole increments. Fractional dragging/keyboard increments and seek-step/tick consistency are tracked for the next iteration in [#49](https://github.com/atcarter714/DXSharp/issues/49).

DirectStorage, current GameInput, X3DAudio/reusable streaming audio, a visual DXR scene and further production resilience remain continuation work. Existing published package versions are immutable.
